# 真实天气（Open-Meteo）+ 定位稳健性（+ 文档纠错）

## Context

HANDOFF_5 §8 的第 7、8 条一直挂着「未排期」：

- **第 7 条**：接真实天气。现在天气只有 `FakeWeatherProvider`（固定晴），而所有玩法条件（雨天湖边掉「湖泊记忆碎片」、雨夜「镜月鱼影」、NPC 的"天气跃迁"主动消息、好感里的 wet 加成）都读它。也就是说**这些内容在真机上一直不成立**。
- **第 8 条**：定位体验。现在精度（`accuracyMeters`）只用于"差于 50m 丢弃轨迹点"，从不显示——站在楼里看不出"为什么没在记录"。而 MagicOS 掐后台定位导致回调长时间不来时，代码里**没有任何反应**（`LocationManager` 降级只在启动那一刻判断一次）。

本轮把这两条做掉，并顺手修掉 8 处与现状冲突的文档。

### 已确认的三个决策

1. 天气数据源用 **Open-Meteo**：非商用免费、**无需 API key**、<10000 次/日。已实测接口可用（`weather_code` 走 WMO 4677）。
2. 天气**保留手动调试切换**（与季节的"自动/手动覆盖"同构）。
3. 定位做**精度指示 + 轻量看门狗**；**不做运行时切换定位源**（会重复发点、弄乱轨迹）。

## 一、真实天气

### 接口与映射

```
https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lng}
  &current=temperature_2m,relative_humidity_2m,weather_code
```
响应（实测）：`{"utc_offset_seconds":28800,"current":{"time":"...","interval":900,"temperature_2m":21.9,"relative_humidity_2m":72,"weather_code":3}}`

不带 `timezone=auto`（我们不用 `current.time`，只在本地按 `WorldClock` 算时段），省一段 payload。

WMO 4677 → `WeatherKind`（纯函数，未知码返回 **null**，调用方保留上次好值而不是猜）：

| 码 | kind |
|---|---|
| 0, 1 | CLEAR |
| 2, 3 | CLOUDY |
| 45, 48 | FOG |
| 51, 53, 55, 56, 57, 61, 63, 80, 81 | LIGHT_RAIN |
| 65, 66, 67, 82, 95, 96, 99 | HEAVY_RAIN |
| 71, 73, 75, 77, 85, 86 | SNOW |

**`WeatherKind.WIND` 永远不可达**（WMO 4677 里风是独立变量，不是天气码）——在 KDoc 写明，否则后人以为漏了。

### 领域新文件

- `domain/world/WeatherSource.kt`：`interface WeatherSource : WeatherProvider { val manualOverride: StateFlow<WeatherState?>; val status: StateFlow<WeatherStatus>; fun setOverride(state: WeatherState?) }` + `fun WeatherSource.setKind(kind) = setOverride(weatherPreset(kind))`。**逐行镜像 `SeasonSource`**（[SeasonSource.kt](file:///e:/DreamingPath/RainingTrace/app/src/main/java/com/rainingtrace/domain/world/SeasonSource.kt)、[DerivedSeasonSource.kt](file:///e:/DreamingPath/RainingTrace/app/src/main/java/com/rainingtrace/domain/world/DerivedSeasonSource.kt)）——`setOverride(null)` = 回到真实来源。
  `data class WeatherStatus(lastUpdatedAtEpochMs: Long?, isRetrying: Boolean)`：把"还没拿到 / 正在重试"放进**独立流**，不要新增 `WeatherKind.UNKNOWN`（它会污染 `WorldLabels.label()` 的穷尽 when、`weatherPreset`，以及**内容 JSON 的合法天气值列表**）。
- `domain/world/WeatherApi.kt`：`interface WeatherApi { suspend fun currentWeather(coordinate: WorldCoordinate): WeatherState? }`——null = 失败，**永不抛异常**。
- `domain/world/WmoWeatherCode.kt`：`fun weatherKindOfWmoCode(code: Int): WeatherKind?`。
- `domain/world/RemoteWeatherSource.kt`：`(api, locationProvider, foreground, cache, clock, scope)`。
  - `weather = combine(_manualOverride, polled) { ov, real -> ov ?: real }.stateIn(scope, WhileSubscribed(5min), initial = cache ?: weatherPreset(CLOUDY))`
  - `polled`：先立即拉一次，成功每 **15 min** 刷新（与 API 的 `interval: 900` 对齐），失败 **1 min** 后重试。
  - 四条跳过规则：**没有定位 fix 时跳过**；**非前台时跳过**；**覆盖值非 null 时跳过**（别白白烧配额）；失败时保留上一次好值。
- `domain/world/WeatherCache.kt`：`suspend fun load(): WeatherCacheEntry?` / `save(entry)`。

### 数据层与接线

- `platform/weather/OpenMeteoWeatherApi.kt`：**零新依赖**。只装了 `ktor-client-okhttp`，但 `HttpTimeout` 在 `ktor-client-core` 里（随它传递进来）；直接 `bodyAsText()` + 私有 `Json { ignoreUnknownKeys = true }` 解码（**不要复用** `ContentJsonFormat`：它是 `data.content` 的 internal 且 `prettyPrint = true`）。
- `data/settings/DataStoreWeatherCache.kt`：复用同一个 `rt_settings` 文件。**坑**：`DataStoreSettingsRepository.kt` 里的 `private val Context.settingsDataStore` 要改成 `internal`——同库再写一个 `preferencesDataStore(name = "rt_settings")` 会在运行期抛 "multiple DataStores active for the same file"。键 snake_case：`weather_kind / weather_humidity / weather_temp_c / weather_fetched_at_ms`。
- **缓存端口是独立的，不要加进 `AppSettingsRepository`**：`NpcProactiveMessageUseCaseTest.FakeSettings`、`ChangeGridLevelUseCaseTest.FakeSettings` 都实现了它，加成员会直接编译失败；而且缓存是"系统记账"不是用户偏好。
- `core/common/AppContainer.kt`：`HttpClient(OkHttp) { install(HttpTimeout) { requestTimeoutMillis = 8_000; connectTimeoutMillis = 5_000 } }`，`by lazy` 且**不关闭**（进程存活期唯一实例；注释说明这是有意的取舍）。`weatherSource: WeatherSource` 替换 `weatherProvider`/`mutableWeatherProvider`；`SystemWorldStateProvider(weatherProvider = weatherSource)` 不用改。缓存首帧沿用既有 `runBlocking` 惯用法（同 `gridManager`、`initialLocationMode`）。

### 设置页

- `SettingsViewModel`：`mutableWeather: MutableWeatherProvider?` → `weatherSource: WeatherSource?`；`canSetWeather = weatherSource != null`；`weatherKind` 取**生效值**；新增 `weatherOverride: StateFlow<WeatherState?>` 与 `setWeatherAuto()`。
- `SettingsScreen` 天气区（L275-293）：顶部加一行「自动（真实天气）」`OptionRow`（`selected = weatherOverride == null`），照抄季节区 L340-345 的写法。
  **必须修的 bug**：每种天气行的 `selected` 要用 `weatherOverride?.kind == kind`，**不能用** `weatherKind == kind`——否则真实天气是多云时"多云"行会被点亮，玩家会以为手动生效了。
- 加 `WeatherStatus` 状态行（"上次更新 21:04" / "还没拿到，正在重试"）与 **Open-Meteo 署名**（`Weather data by Open-Meteo.com (CC BY 4.0)`，免费条款要求）。
- 删掉 `domain/world/WeatherState.kt` 里的 `MutableWeatherProvider`（被 `WeatherSource` 取代，留两个可变语义会让人猜该调哪个）；`FakeWeatherProvider` 改成实现 `WeatherSource`（`WorldStateTest:118` 一行都不用动）。
- **湿度必须 `/100.0` 再 `coerceIn(0.0, 1.0)`**：API 给的是 72，而 `WeatherState.init` 有 `require(humidity in 0.0..1.0)`；台站偶发 101，不钳位就会在解析路径里抛出——这正是"永不抛异常"最容易漏的一处。

## 二、定位

### (a) 精度指示

- `domain/map/LocationQuality.kt`：`enum LocationQuality { GOOD, FAIR, POOR, UNKNOWN }` + `fun locationQualityOf(accuracyMeters: Double?): LocationQuality`（GOOD ≤15m / FAIR ≤50m / POOR >50m / null → UNKNOWN）。**50m 分界与 `RecordTrackPointUseCase.MAX_ACCURACY_METERS` 精确对齐**，所以 POOR 就等于"点正在被丢弃"，写进 KDoc。中文文案放 `core/ui/`（跟 `WorldLabels` 一个口径）。
- `MapUiState` 加 `lastAccuracyMeters: Double?`，在 `onLocationFix` 里**在 reject 闸门之前**填充（被拒的点也要让质量可见）。
- **不新增第三个 chip**：左上角已经会堆到 4 个，把精度并进现有 GRANTED 分支的文案（`"GPS 定位中 · 精度 12 m"` / `"GPS 定位中 · 信号弱"`）。**仅在 `locationMode == GPS` 时渲染**（Fake 的 5.0m "GOOD" 是误导）。

### (b) 轻量看门狗

- `domain/map/LocationWatchdog.kt`：**纯决策函数**（可 JVM 全覆盖），返回 `WAIT / PROBE_LAST_KNOWN / RE_REQUEST / WARN`。阈值 90s / 180s / 300s。
  **必须是边沿触发、按优先级短路**，不能写成按区间匹配（否则每分钟 tick 在同一区间里重复返回 PROBE）：
  ```
  if (silent < PROBE) WAIT
  if (!probeDone) PROBE
  if (silent < RE_REQUEST) WAIT
  if (!reRequestDone) RE_REQUEST
  if (silent < WARN) WAIT else WARN
  ```
  `probeDone/reRequestDone` 的语义是"本轮静默期内已试过"，**每次收到 fix 必须双清**；`stop()` 也要清。
- `AndroidLocationProvider` 接线：
  - 新增 `scope` 参数与 `lastCallbackAtMs`（在 `emitLocation` 里更新）、`lastEngineFused`、`stalled: StateFlow<Boolean>`。
  - watchdog 协程跑在 **`Dispatchers.Main.immediate`**：`fusedClient/fusedCallback/locationManager/managerListener` 全非 `@Volatile`，只在主线程被触碰；放后台线程就是新增跨线程竞争。
  - **只在前台默认档运行**（`running && passiveIntervalMs == null`）。后台 15 min 档的静默是预期的。
  - **抽出 `restartSameEngine()`，绝不降级**：重发时只走同一个引擎；fused 重发失败直接 `running = false` 并进 WARN，**不要**走 `tryStartLocationManager()`——那会静默把采集源换掉，正是被否掉的语义。
  - `setPassiveIntervalMs(null)`（回到前台档）时**必须重置 `lastCallbackAtMs` 与两个标志**，否则从后台回来会立刻误报 WARN。进入被动档时也要 `stalled = false`（否则提示留在屏幕上）。
- `domain/map/LocationHealth.kt`：`interface LocationHealth { val stalled: StateFlow<Boolean> }`——**不要塞进 `LocationProvider`**（否则 `FakeLocationProvider` 被迫实现）。`SwitchableLocationProvider` 实现它并直接委托 `android.stalled`（Fake 模式恒 false）。
- 文案：`"定位卡住了 · 去系统设置允许后台定位"`。MagicOS 的真实成因是省电策略冻结后台，不是没给权限，所以**不做深链跳转**，只说清去哪儿。

Honor 100 的 `logcat` 对第三方应用基本被裁掉，**只按 UI 验收**（实机部分交给你）：

## 六、非目标

不加 `WeatherKind.UNKNOWN`；不做天气预报/历史/多日缓存；不做按经纬度的天气网格；不做多天气源可切换；不做 API key；不做重试退避曲线（固定 1 min）；不做定位源运行时切换（你已否）、双源融合、深链跳转；不引入任何新依赖（ktor content-negotiation 也不要）；不做缓存过期淘汰（命中即用，状态行显示时间）。
