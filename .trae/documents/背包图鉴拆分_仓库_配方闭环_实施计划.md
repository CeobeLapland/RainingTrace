# 背包/图鉴拆分 · 仓库 · 配方加工闭环 —— 实施计划

## Context

当前 `InventoryScreen` 把"背包"和"图鉴"合在一个页面：它拿资源目录 `catalog.all()` 与库存数量合并，用 `quantity > 0` 反推"是否已收集"（[InventoryViewModel.kt](file:///e:/DreamingPath/RainingTrace/app/src/main/java/com/rainingtrace/feature/inventory/InventoryViewModel.kt#L38-L52)）。这在"只增不减"的当下能跑，但只要出现**消耗**（合成扣原料、物品搬进仓库），已被采到过的条目会自己变灰——"我明明采到过"被抹掉。

同时，后面的目标（星露谷/我的世界式的采集→加工→存放）需要三样现在没有的东西：一个会变的**随身容器**、一个**永久的知识档案**、一个**家园存储**。内容层也还没有"配方"这一类，18 种资源清一色是 tier-0 采集物、没有用途（见 [resources.json](file:///e:/DreamingPath/RainingTrace/app/src/main/assets/content/resources.json)）。

本轮把这三块地基打上，让采集第一次有"出口"：

- **A. 背包 / 图鉴拆成同一入口的两个页签**，并把「已发现」从数量解耦（改从足迹事件派生）。
- **B. 仓库**（新容器，入口在「我的」页），背包↔仓库存取；堆叠上限展示 + **软容量**（只提示不阻止）。
- **C. 配方 / 加工最小闭环**：新内容类型 `recipes.json` + 少量基材/加工品 + 制作 UseCase + 背包内随时制作。

不在本轮：资源点随机刷新（spawn）——按 [HANDOFF_4 §6](file:///e:/DreamingPath/RainingTrace/doc/handoff/HANDOFF_4.md) 的依赖顺序，等明天美术图标换完再上。

遵循既有约定：手写 DI、Compose stateless + UiState、domain 禁 Android SDK、所有时间注入 `WorldClock`、**内容只住在 JSON 里**、新逻辑尽量落 domain 纯函数（数据层无 Robolectric 单测）。

## 关键设计取舍（已定）

- **「已发现」的真相在足迹事件里**，不在库存数量里。与既有先例同构（NPC"见过谁"从 `NPC_MET` 派生）。成功结算总会写 `FootprintEventType.PLACE_OBSERVED` 且 payload 带 `resourceId`（[PerformPlaceActionUseCase.kt](file:///e:/DreamingPath/RainingTrace/app/src/main/java/com/rainingtrace/domain/exploration/PerformPlaceActionUseCase.kt#L72-L87)），所以**不加表、不加迁移**。
- **发现口径 = 足迹事件 ∪ 当前持有**。只认事件会漏掉"制作产出"（制作不写足迹），所以并入 inventory/warehouse 的 `firstAcquiredAtEpochMs`。
- **仓库复用 `InventoryState` / `InventoryItem` / `RoomInventoryRepository`**，只多一个 Entity + Dao。warehouse 表与 `inventory_items` 同 4 列。**刻意不动 `inventory_items` 与既有 `saveState` 路径**（避免 `replaceAll` 的 `deleteAll` 误删仓库行）。
- **搬运动作原子**：domain 纯函数算出"两边的新状态"，数据层用**一个 `@Transaction` DAO 方法**一次写完两张表（照既有 `replaceAll` 的形状）。不做两次顺序 `saveState`（崩溃会丢/复制物品）。
- **软容量语义钉死**：`stackLimit` 管单个资源的数量、软上限管背包的**种类数**、两者**只提示不阻止**、仓库不计入软上限。避免"堆叠上限"和"软容量"互相打脸。
- **配方与产出规则保持两套**：recipe 是确定性的"输入→输出"，无地点无冷却；`ResourceYieldRule` 是"世界条件→单向产出"。统一会让两者都变形。制作也**不**复用 `PlaceActionType`（那会破坏"动作必须在 `place.actions` 且要过距离校验"的不变式）。
- **制作只从背包取材**；材料在仓库时明确拒绝并提示"材料在仓库里"。
- 制作**不写足迹事件**（`FootprintEvent` 强制带 coordinate，MVP 不值得为它接 `LocationProvider`）。

## 风险与提醒

- `TransferItemUseCase` 的两表写入**必须**收敛进单个 `@Transaction`，不能连调两次 `saveState`。
- 图鉴的 `eventsOfType(PLACE_OBSERVED)` 是全表 + payload 全解码，**不要**订阅库存流；按页签刷新。spawn 上线后若变慢，再考虑加 payload 键列或物化表。
- 手动 `ALTER` 与 schema json 不一致会崩；Boolean 是 `INTEGER NOT NULL`，可空列不能带 `NOT NULL`。
- Kotlin 注释里写 `content/*.json` 会因块注释可嵌套而编译失败（`Unclosed comment`）——写文件名时避开 `/*`。
- `preferencesDataStore` 同一份文件只能有一个委托；本轮不需要新的 DataStore。
- `ResourceDefinition.stackLimit` 一定给默认值，否则波及下游构造点。
