# RainingTrace / 雨迹 — 地图、定位与 AR 专项

## 1. 地图的职责边界

地图只负责：

- render
- camera
- gesture
- visual layer
- location marker

地图不负责：

- 玩家资源
- 探索判定
- 任务奖励
- 金币
- 记忆
- NPC 逻辑

## 4. 定位

### 位置采样不是游戏事件

`LocationSample` → 经过过滤 → 才可能触发 `PlayerMoved`。

过滤条件：

- accuracy
- timestamp freshness
- horizontal jump
- minimum movement threshold
- stationary debounce

### 推荐事件层

```text
Raw Location
 ↓
Location Filter
 ↓
Stable Location
 ↓
Cell Mapping
 ↓
Exploration Rule
 ↓
Game Event
```

---

## 5. 避免“GPS 打游戏”

不要每次定位更新都：

> 发网络请求。

P0：

- 本地计算 cell
- 聚合 movement
- 批量同步

P1：

- 后台同步
- server validation

## 6. 路径/足迹

玩家足迹不是原始 GPS dump。

默认采用：

- 时间 bucket
- 空间 bucket
- Douglas-Peucker 或等价简化
- 精度等级
- visibility policy

目标：

> 保留“你去过哪里”的感觉，而不是记录一份高精度监控轨迹。

## 8b. 定位质量与"卡住"的可见信号

这一节是 `HANDOFF_5 §8` 第 8 条的正式口径。

**精度等级**（`domain/map/LocationQuality.kt`）：

| 等级 | 精度 | 含义 |
|---|---|---|
| GOOD | ≤ 15 m | 可靠 |
| FAIR | ≤ 50 m | 可用，已在护栏附近 |
| POOR | > 50 m | **轨迹点正在被丢弃** |
| UNKNOWN | 无定位 | 还没拿到 |

`POOR` 的分界线**就是** `RecordTrackPointUseCase.MAX_ACCURACY_METERS`（50 m）。这不是巧合：界面上的"信号弱"必须与系统实际行为是同一件事，否则就是骗人。UI 里 `POOR` **刻意不给米数**——一个精确的数字会让人以为"再等一会儿就好"，而实际上点正在被丢。

**看门狗**（`domain/map/LocationWatchdog.kt` + `LocationHealth`）：Honor/MagicOS 会用省电策略掐掉后台定位，回调变得极稀。代码修不了系统策略，能做的是**发现 → 补救 → 如实说出来**：

- 静默 90 s → 探一次系统缓存位置（便宜，常常立刻就有）；
- 静默 180 s → **用同一个引擎**重发一次请求（**绝不降级换源**：那会重复发点、弄乱轨迹）；
- 静默 300 s → 亮出 `stalled`，地图上提示"定位卡住了 · 去系统设置允许后台定位"。

三条硬约束：

1. **只在前台默认档判定**（`running && passiveIntervalMs == null`）。后台 15 分钟档的静默是预期行为。
2. **收到真实回调 / `stop()` / 换档都要重置**计时与标志位。漏掉"从后台回到前台"这一处，就会立刻误报。
3. 决策必须**边沿触发**（用 `LocationWatchdogState.consume` 而不是裸调纯函数），否则静默区间里每个 tick 都会重复执行同一个补救。

## 10. AR 阶段

> 本节只定义阶段名与边界；**具体实现路径、设备前提、精度事实与素材需求见 `12_AR实现路径与阶段规划.md`**。

### AR-0：Local AR

- 平面检测
- 点击放置
- 一个虚拟物件
- 无世界定位

### AR-1：地点 AR

- 现实地点附近出现虚拟物件
- 基于 GPS + local orientation
- 允许误差

### AR-2：Geospatial AR

- WGS84/Terrain/Rooftop anchor
- VPS
- 大规模地点绑定

Google ARCore Geospatial API 已支持通过 GPS、设备传感器与 VPS 建立地理空间定位，并提供地理 anchor。citeturn765638search3turn765638search15

## 11. AR 必须支持失败

所有 AR feature 必须设计：

```text
SUPPORTED
INITIALIZING
READY
TRACKING_LOST
UNSUPPORTED
PERMISSION_DENIED
ERROR
```

任何状态都不能把用户卡死在黑屏相机页面。

## 12. 相机/随手拍

CameraX 负责：

- capture
- preview
- image metadata
- orientation

业务层拿到：

```text
CapturedMedia
- localUri
- capturedAt
- locationOptional
- orientation
- mimeType
```

照片分析、标签和资源识别再走后续 pipeline。

---

## 13. “随手拍”处理流水线

```text
Camera
 ↓
CapturedMedia
 ↓
Local Draft
 ↓
Optional On-device preprocessing
 ↓
Upload
 ↓
Vision / classification (optional)
 ↓
Game interpretation
 ↓
Memory / Resource / Discovery
```

必须允许用户先保存照片，再慢慢处理。

## 14. 地图性能

禁止一次渲染整个城市所有实体。

使用：

- viewport query
- zoom-level filtering
- clustering
- tile/region based loading
- local cache

---

## 15. 第一版只覆盖“小而密”的区域

建议：

> 一个校园 / 大学园区 / 高密度可步行社区。

不是城市级全地图。

因为《雨迹》最重要的是：

> 一个地方里“有什么”。

不是：

> 地图有多大。
