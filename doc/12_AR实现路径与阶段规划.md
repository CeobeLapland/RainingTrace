# RainingTrace / 雨迹 — AR 实现路径与阶段规划

> 文档定位：`06_地图_定位_AR专项.md` §9–§11 的**展开实现篇**。
> 06 定义"AR 的架构边界与阶段名（AR-0/1/2）"，本文回答"具体怎么做、走哪条路、要什么素材、精度到哪、怎么分阶段"。

---

## 0. 一句话结论

《雨迹》的 AR 有四条路可走：**ARCore**、**华为 AR Engine**、**EasyAR Sense**、**罗盘 AR**。

**本机（国内版 / 无 Play / 无 HMS）实测结论（2026-09-19）**：

- **ARCore 确定不可用**（无 Play 商店 → 装不了 ARCore 运行时）。
- **华为 AR Engine 已出局**（无 HMS Core、无 AR Engine 服务、华为应用市场也搜不到「AR测量」；这些不是用户能自行补上的）。
- **本机只剩两条路可用**：**EasyAR Sense**（真 3D、不依赖 ARCore/HMS）与 **罗盘 AR**（零依赖兜底）。

**推荐顺序**：

1. **EasyAR Sense 是"本机真 3D"的唯一第三方路线**——若想要真 3D 平面放置，这是首选；个人版免费可先做原型（不可商用 + 有水印）。
2. **罗盘 AR** 是最零依赖、立刻能上的兜底，用于先验证"AR 是出口"的产品手感。
3. ARCore / 华为 AR Engine 在本机不可用，留作**将来换设备或支持多厂商**时再考虑。

> 注：早期记录"HANDOFF 有 GMS"与实测矛盾，以实测为准。

## 1. 当前实现现状（代码事实，非计划）

现有代码已经完成 AR-0 的**全部地基**，这是本次讨论的起点：

| 文件 | 已实现内容 |
|---|---|
| `platform/ar/ArCoreController.kt` | ARCore `Session` 创建与能力检测；OES 纹理相机背景（GLSL）；`frame.hitTest` 平面命中；`Anchor` 创建；锚点 → 屏幕归一化坐标投影（MVP 矩阵）；跟踪状态机 |
| `feature/ar/ArScreen.kt` | `GLSurfaceView` 承载相机背景；**Compose 精灵叠加**（发光圆点）；点击放置；失败降级卡片 |
| `domain/ar/ArModels.kt` | `ArSessionState` 状态机、`ArObject`、`PlacedArObject`、`ArController` 接口 |

**关键设计资产（不要推翻）**：

1. **ARCore 类型只存在于 `platform/ar`**，domain/feature 只见 `ArController` —— 符合 `06` §9 的分层约束，也是未来换实现的前提。
2. **虚拟物体是"屏幕空间投影 + Compose 叠加"，不是 3D 渲染管线**。这意味着当前架构下"加一个物体"的成本极低，但也意味着**现在还画不出 3D 模型**。
3. **所有失败路径都有显式状态**（`UNSUPPORTED` / `PERMISSION_DENIED` / `ERROR` / `TRACKING_LOST`），绝不黑屏 —— 符合 `06` §11。

### 1.1 当前的阻塞点（已实测确认）

设备（Honor 100 / MAA-AN00 / MagicOS，**国内版 ROM**）的实测情况（2026-09-19）：

| 检查项 | 结果 |
|---|---|
| Google Play 商店 | **无**（装的是华为应用市场） |
| Google Play Services for AR | **无法安装** → **ARCore 确定不可用** |
| HMS Core（华为移动服务） | **无**，系统包里也搜不到 |
| AR Engine 服务 | **无** |
| 华为应用市场「AR测量」 | **搜不到** |

**结论：这台设备上，两条"真 3D"原生路线（ARCore / 华为 AR Engine）全部不可用。**

- ARCore：`Session(context)` 抛 `UnavailableException` → 状态落到 `UNSUPPORTED` → 用户看到降级卡。
- 华为 AR Engine：缺少运行前提（HMS Core + AR Engine 服务），**且这两个都不是用户能自行补上的**——AR Engine 依赖设备级的相机标定与系统服务，不是装个 APK 就能有。

**所以：本机 AR 从未真正运行过，且短期内不可能通过"装点什么"解决。**

> ⚠️ **注意与历史记录的矛盾**：`doc/handoff/HANDOFF_1.md` §3 与 `HANDOFF_2.md` §3 记录该机"有 GMS"，与实测不符。**以实测为准**，这条记录应在下次更新 HANDOFF 时修正。

**本机剩余可选项**：只有 **EasyAR Sense**（不依赖 ARCore/HMS）与 **罗盘 AR**（只依赖摄像头+传感器）。

## 3. 路线①：ARCore 平面 AR

### 3.1 原理

用摄像头做**视觉 SLAM**：识别画面中的特征点，反推出手机在空间中的位姿（6DoF），并检测出水平面。点击屏幕 → `hitTest` 射线打到平面上 → 在该点创建一个 `Anchor`（锚点）。锚点绑定在**局部坐标系**里，之后每帧把锚点位置用相机视图/投影矩阵投到屏幕上。

### 3.2 现有代码能直接做什么

**侧载 ARCore 成功的话，现有代码立刻可用**：点击地面 → 一个发光精灵钉在那里，你绕着走它不飘。这就是 AR-0 的验收点，**零代码改动**。

### 3.3 精度与持久化（重要事实）

- **局部精度极高**：厘米级，短会话内物体视觉上"焊"在原地。
- **但它不是地理坐标**：是手机开机后自建的局部坐标系。**退出 AR / 重启 App 后锚点消失**。
- 想跨会话持久需要 **Cloud Anchors** 或 **Geospatial API**：
  - Cloud Anchors：需 Google Cloud 项目 + 联网解析，锚点有有效期（通常 1 天~1 年，取决于持久化等级）。
  - Geospatial API：需要 **VPS（视觉定位服务）街景覆盖**，中国大陆覆盖极差。
  - **结论：本阶段不做跨会话持久化。** 这是另一个量级的工程，且国内可用性存疑。

### 3.4 设备前提与验证（对本机：已确认不可用）

**本机无 Google Play 商店**，因此**无法安装 "Google Play Services for AR"，ARCore 确定不可用**（见 §1.1）。本小节仅记录——若将来换一台有 GMS/Play 商店的设备，ARCore 才可能可用。

对支持 ARCore 的设备，标准做法是：

1. 用 `ArCoreApk.checkAvailability` + `requestInstall` 检测/安装运行时。
2. 打开 AR 屏判定：能点击放置 → 可用；否则走降级卡。

> 侧载 APK 的方案（早期 HANDOFF 曾提及）只对"有 GMS 但没装运行时"的设备有效；本机连 GMS/Play 都没有，不适用。
>
> **本机的真 3D 路线应转向华为 AR Engine（见 §6.1）。**

### 3.5 如果要做"真 3D 模型"

现有架构是"屏幕投影 + Compose 叠加"，**画不出 3D 模型**。要做需要新增渲染管线，两条子路线：

| 方案 | 说明 | 评价 |
|---|---|---|
| 引入 SceneView / Filament | 现成的 glTF 渲染库，几十行接入，支持光照/动画 | **若必须做 3D，选这条** |
| 手写 GLES + 自研模型加载 | 完全可控，但要走通 glTF 解析、蒙皮、光照 | 不要做，性价比极低 |

> 另有社区方案 **Sceneform-EQR**（用已停更的 Sceneform API 做渲染桥接），见 §6。它只解决"怎么画 3D"，不解决"设备支不支持"。

**即使走①，也建议第一版先用"贴在平面上的精灵"**，把"物体稳稳站在地上"跑通，再升级 3D 模型管线。一上来做模型加载 + 骨骼动画 + 光照，是给自己挖坑。

### 3.6 风险清单

- 设备认证不确定（最大风险）。
- 弱纹理环境（纯白墙、空地、暗光）跟踪会丢失 → 必须有 `TRACKING_LOST` 提示与恢复。
- 发热耗电严重（相机 + SLAM + GPU 同时满载）。
- 3D 管线一旦引入，包体积与构建复杂度显著上升。

## 4. 路线②：罗盘 AR（零依赖，先验证手感）

### 4.1 原理

不依赖 ARCore。用三样东西合成"虚拟物体钉在现实方向上"的错觉：

```
CameraX 相机预览        →  画面（已跑通，见 CameraXController）
SensorManager           →  ROTATION_VECTOR 传感器 → 手机朝向（方位角/俯仰/横滚）
GPS                     →  玩家当前位置
目标点经纬度（地点/记忆） →  计算目标相对玩家的方位角与距离
                        ↓
方位角 − 手机朝向 = 相对夹角 → 投影到屏幕 x
俯仰角                        → 投影到屏幕 y
距离                          → 决定精灵缩放/透明度
```

转头时手机朝向变化 → 精灵在屏幕上跟着移动，形成"钉在现实方向上"的效果。

### 4.2 架构落点（遵守现有分层约定）

| 层 | 新增内容 |
|---|---|
| `domain/ar` | `ArAnchorType.WORLD_BEARING`；`BearingMath`（纯 Kotlin，**可写 JVM 单测**）：经纬度 → 方位角/距离，相对夹角 → 屏幕坐标 |
| `domain/sensors` | `OrientationProvider` 接口（`Flow<DeviceOrientation>`：azimuth/pitch/roll） |
| `platform/sensors` | `SensorOrientationProvider`（`SensorManager` + `ROTATION_VECTOR`，低通滤波） |
| `platform/ar` | `CompassArController`（实现 `ArController`，与 `ArCoreController` 平级，可切换） |
| `feature/ar` | `ArScreen` 增加"罗盘模式"渲染分支；目标选择入口（最近地点 / 某条记忆） |

**关键点**：因为 `ArController` 已经是接口，**罗盘实现可以直接替换 ARCore 实现**，`ArScreen` 的叠加逻辑几乎不用改 —— 这是当初分层做对了的红利。

### 4.3 数学要点（实现时参考）

- **目标方位角**（大圆航向）：
  ```
  bearing = atan2( sin(Δλ)·cos(φ2),
                   cos(φ1)·sin(φ2) − sin(φ1)·cos(φ2)·cos(Δλ) )
  ```
- **相对夹角** = `normalize(bearing − deviceAzimuth)`，归一到 `[-180°, 180°]`。
- **屏幕 x** ≈ `centerX + (relativeAngle / horizontalFov) * screenWidth`（用设备水平 FOV 做线性映射，MVP 足够）。
- **屏幕 y** ≈ 由俯仰角映射；简化为"精灵底部贴地平线"即可。
- **缩放** ≈ `clamp(k / distance)`，体现"走近变大"。

> 严格做法是把方向向量经相机内参投影；MVP 用 FOV 线性映射即可，误差不影响体验验证。

### 4.4 能做到 / 做不到

**能做到**
- 虚拟生物/物品"站在现实的方向和地点上"，转头它跟着移动，走近它变大。
- 多目标（多个地点/记忆）同时钉在不同方向。
- 因为锚的是经纬度，**离开再回来它还在**（这是路线①给不了的）。

**做不到**
- 贴地、遮挡、精确锚定。
- 罗盘有 ±5~15° 磁干扰漂移（金属、磁吸壳、车辆、电梯）。
- 距离靠 GPS，±5~10m，只适合"大致方位"。

### 4.5 稳定性措施

| 问题 | 措施 |
|---|---|
| 方位角抖动 | 低通滤波（指数平滑），丢弃 `accuracy` 差的样本 |
| 磁干扰漂移 | 提示"请远离金属/磁性物体"；提供"重新校准"手势（8 字晃动） |
| GPS 跳动 | 复用现有 `RecordTrackPointUseCase` 的去噪闸门，取稳定点 |
| 目标在背后 | 屏幕边缘显示方向箭头而非隐藏（避免"东西不见了"） |
| 传感器缺失 | 落到 `UNSUPPORTED` 状态，显示降级卡（复用现有状态机） |

### 4.6 精灵素材需求（回答"要不要提供模型"）

**罗盘 AR 不需要 Blender 模型。** 按投入从低到高：

| 档位 | 素材 | 效果 |
|---|---|---|
| 0（默认） | **代码画的占位图形**（发光圆/光点，复用现有 `ArScreen` 精灵） | 零阻塞，先跑通 |
| 1 | **一张透明 PNG**（如"湖之精灵"） | 立刻有辨识度，**推荐** |
| 2 | **PNG 序列帧**（4~8 帧循环，如轻微浮动） | 有生命感，成本仍低 |
| 3 | 3D 模型 `.glb` | **罗盘 AR 用不上**，只有路线①的真 3D 才需要 |

**结论：你可以先给一张透明 PNG，也可以先用占位图形；不需要现在做 3D 模型。** 若将来做路线① 的 3D，再在 Blender 里导出 **glTF 2.0（.glb，动画烘焙进去）**。

### 4.7 工作量与切片划分

约 **200~300 行**，可拆成 3 个可独立验收的切片：

1. **AR-C1 传感器层**：`OrientationProvider` + `SensorOrientationProvider` + 滤波；单测覆盖 `BearingMath`。
2. **AR-C2 罗盘渲染**：`CompassArController` 实现 `ArController`；`ArScreen` 罗盘模式；放置单个目标。
3. **AR-C3 目标绑定**：从地图地点/记忆选目标 → 进入 AR → 多个目标按方位分布；屏幕边缘方向箭头。

## 5. 路线③：EasyAR Sense（真 3D、不依赖 ARCore）

### 5.1 为什么值得评估

它补上了核心空缺：**一台不支持 ARCore 的设备，也能拿到真正的 3D 平面放置 AR**。

| 事实 | 说明 |
|---|---|
| 独立性 | **不依赖 ARCore / 华为**；官方宣称"兼容主流不被 ARCore 支持的 Android 机型" |
| 能力 | Motion Tracking（视觉惯性 SLAM）、Surface Tracking（表面跟踪）、稀疏/稠密空间地图、平面图像/3D 物体跟踪 |
| 语言 | **提供 Java/Kotlin API for Android**（不用啃 C++） |
| 授权 | **个人版免费**（独立开发者、不可商用、有 EasyAR 水印、自定义相机每次运行停 100 秒）；专业版约 ¥258/月（可商用）；经典版约 ¥8999 一次性 |
| 平台 | 国内厂商，中文文档友好 |

### 5.2 做法（与 ARCore 平行的适配层）

原则：**不改 domain/feature，把 `ArController` 换一个实现**。

1. 申请 EasyAR 账号，取得 Personal/Pro license key。
2. 配依赖 + license key，初始化 motion tracker（对标 ARCore `Session`）。
3. 接相机帧（EasyAR 有自定义相机接口）→ 表面跟踪识别平面 → 点击放置。
4. 渲染层：可用它自带的 GL 渲染，或仍走 `ArCoreController` 那套"投影到屏幕 + Compose 叠加"精灵式演示（MVP 足够）。
5. 复用现有 `ArSessionState` 状态机做失败降级。

### 5.3 坑 / 注意

- **个人版不可商用**：原型随便用；真要上架商用须转付费（¥258/月 或 ¥8999）。
- **个人版自定义相机每次运行 100 秒限制**：若走"系统相机全屏"可能不触发，但用自定义相机接入会触发，需实测确认对体验的影响。
- **一次性授权绑定单个 App**：多 App 重复购买。
- 社区 / 资料量比 ARCore 小，但中文文档 + 示例齐全，足够。

### 5.4 前提与取舍

**先做 AR-P1（验证华为 AR Engine）**。取舍逻辑：

- **若 AR Engine 可用** → 优先用它（免费、真 3D、能复用现有架构），不必引入第三方 SDK。
- **若 AR Engine 不可用，或你不想把 AR 锁死在华为生态** → 再评估 EasyAR Sense。
- 引入 EasyAR 属 L2 决策，能省则省。

## 6. 其他方案评估

### 6.1 华为 AR Engine（本机：已实测出局）

**是什么**：华为自研 AR SDK（对标 ARCore），提供平面检测（ARWorld）、手势（ARHand）、面部（ARFace）等能力。它跑在 **HMS Core（华为移动服务）** 之上，且依赖**设备级的 AR Engine 系统服务与相机标定**。

**本机实测（2026-09-19）**：

| 检查项 | 结果 |
|---|---|
| HMS Core（华为移动服务） | **无**（系统包里也搜不到） |
| AR Engine 服务 | **无** |
| 华为应用市场「AR测量」 | **搜不到** |

**结论：本机不可用，且不是"装个 APK 就能补上"**——AR Engine 需要系统级服务与出厂相机标定，通常只有华为/荣耀的对应机型才具备。虽然本机有华为应用市场，但那只是应用商店，**不等于具备 HMS 框架**。

**什么时候重新考虑**：

- 换一台**内置 HMS 的华为/荣耀设备**（需实测确认「AR测量」可用）；
- 或产品要正式支持华为生态时（届时仍需 AGC 工程配置 + 华为开发者账号）。

**若将来在支持的设备上要做**（记录备查）：

| 步骤 | 说明 |
|---|---|
| 依赖 | 华为 Maven 仓库 + `com.huawei.hms:arenginesdk`；需华为开发者账号与 AGC 配置 |
| 适配器 | 新增 `ArEngineController` 实现现有 `ArController` 接口。`ARSession` / `ARFrame` / `hitTest` 概念与 ARCore **平行**，可对照 `ArCoreController` 改写 |
| 渲染 | 最省的做法：继续用"投影到屏幕 + Compose 精灵"，渲染层零新增。真 3D 模型需自建渲染层 |
| 代价 | 锁定华为生态；产品化需同时维护 ARCore + AR Engine + 兜底（L1 适配成本） |

### 6.2 Sceneform-EQR（不推荐：只是渲染桥接）

华为开发者做的**开源桥接层**：用 Google 已弃用的 Sceneform 渲染 API，去渲染 **AR Engine / ARCore / ORB-SLAM** 的追踪结果。

- **它不是 SLAM 引擎**，解决不了"设备支不支持 AR"；只在"已有可用追踪引擎"时帮忙画 3D。
- Sceneform 已被 Google **归档停更**，站在废弃轮子上。
- 角色定位：如果将来走 AR Engine 且需要画 3D 模型，它可作为**渲染层候选之一**（与 Filament 并列比较），但不是决策主角。

### 6.3 WebXR / 8th Wall（不推荐）

WebXR 的 AR 模块底层同样依赖 ARCore，绕不开；商业 SDK 成本高；还引入 WebView。

### 6.4 手搓 SLAM / 深度估计（不推荐）

那是"高级"，不是"能用"。不要做。

## 7. 阶段规划

| 阶段 | 目标 | 前提 | 验收标准 | 对应任务树 |
|---|---|---|---|---|
| **AR-P0**（已完成） | 本地平面放置一个虚拟物件 | — | 支持设备上可点击放置；不支持设备走降级卡不黑屏 | RT-AR-001~004 |
| **AR-P1**（已完成） | **设备能力验证** | — | ✅ 结论：本机 ARCore 与华为 AR Engine **均不可用**；真 3D 只剩 EasyAR | — |
| **AR-P2** | **罗盘 AR 最小可用**（最零依赖，先验证手感） | 无 | 转头时精灵钉在现实方位；走近变大；离开重进仍在；传感器缺失走降级 | RT-AR-005~007 |
| **AR-P3** | **真 3D 平面 AR**：**EasyAR Sense**（本机唯一真 3D 路线） | 接受第三方 SDK + 授权条件 | 平面点击放置物体；贴合稳定；失败降级 | RT-AR-008~009 |
| **AR-P4** | **地点绑定 AR（AR-1）** | AR-P2 或 AR-P3 | 从地图某地点进入 AR，对应位置/方向出现对象；多目标共存 | RT-AR-010+ |

**推进原则**：AR-P1 决策闸门**已关闭**——本机走不了 ARCore / AR Engine。剩下的是"罗盘 AR（免费/粗）"与"EasyAR（免费个人版/真 3D/不可商用）"之间的取舍。AR-P2 成本最低，用于尽早拿到"第一口 AR 体验"验证手感。

## 8. 给非技术背景的注意事项

1. **本机的 ARCore 是死路**：国内版 ROM 无 Play 商店，装不了 ARCore 运行时。现有的降级卡逻辑是**资产，不要删**。
2. **相机 + GL + 生命周期是最折磨人的部分**（黑屏、旋转错位、切页崩溃），**这部分已经趟平了**，各条路线都能吃到红利。
3. **发热耗电**：AR 同时开摄像头 + 传感器 + GPU，几分钟就烫。AR 会话要做短、随时能退。
4. **安全边界**（GDD §22）：不要引导玩家边走边盯屏幕，尤其湖边、马路、夜间。
5. **不要追求"锚点永久持久化"**：那是 Cloud Anchor / VPS / EasyAR SpatialMap 云服务的领域，国内可用性存疑且工程量级不同。
6. **AR 是出口不是入口**：AR 失效不能影响地图/记忆/日记主循环 —— 这是 `06` §11 的硬约束。
7. **第三方 SDK 是长期负债**：EasyAR 一旦引入，就多了"授权、水印、版本升级、商用付费"四件事要管。**能不用就不用**，只在 ARCore 确认不可用时才评估。

## 10. 待验证技术事实（不要当成结论用）

| 事实 | 为什么重要 | 验证方式 |
|---|---|---|
| EasyAR Sense 个人版真机表现（水印位置、100 秒限制是否触发、SLAM 稳定性） | 决定本机真 3D 路线是否可行 | 跑 EasyAR 官方 Sample |
| EasyAR 是否真能在无 GMS/HMS 的国内 ROM 上跑 | 这是本机唯一真 3D 希望，必须实测 | 同上 |
| 该机 `ROTATION_VECTOR` 传感器是否存在、精度如何 | 决定罗盘 AR 可行性 | 写 provider 后打日志 |
| 该机磁干扰实际漂移幅度 | 决定罗盘 AR 是否"够用" | 真机对照地图方向 |
| 相机水平 FOV 实测值 | 决定罗盘投影映射系数 | 用已知距离物体标定 |

**已确认（不再是待验证项）**：本机 ARCore 不可用（无 Play 商店）；本机华为 AR Engine 不可用（无 HMS Core / 无 AR Engine 服务 / 「AR测量」搜不到）。
